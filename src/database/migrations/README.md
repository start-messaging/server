# Running migrations

## ⚠️ `migration:run` targets whatever `.env` points at

`src/database/data-source.ts` calls `dotenv.config()`, so `npm run migration:run`
reads `server/.env` — which is currently your **production RDS instance**.

`dotenv` does not override variables already present in the environment, so you
can safely aim a run somewhere else by exporting them inline:

```bash
DATABASE_HOST=localhost DATABASE_NAME=sm_db \
DATABASE_USERNAME=postgres DATABASE_PASSWORD=… \
npm run migration:run
```

Always confirm the target before running:

```bash
npm run migration:show    # lists applied [X] and pending [ ] migrations
```

## Folded into `ConsolidatedSchema`: `PerformanceIndexes`

> No longer a separate file — collapsed into `1785500000000-ConsolidatedSchema`
> along with five others. Kept here because the cost, lock and plan measurements
> below still describe what those indexes do, and the index/query coupling
> warning further down is still live.

### What it does

Creates the `pg_trgm` extension and 22 indexes. **Nothing else.** No table,
column, constraint, enum or row is created, altered or dropped, so no user data
can be lost by running or reverting it.

### Cost

- Adds roughly **24 MB** of index data at current volumes.
- Each `CREATE INDEX` briefly holds an ACCESS EXCLUSIVE lock on its table.
  Measured against a restore of production, the largest single build
  (`messages`) held that lock for **321 ms**; the rest are far smaller.
- Every statement is `IF NOT EXISTS`, so re-running is a no-op.

### To run

```bash
cd server
npm run migration:show    # confirm PerformanceIndexes is pending
npm run migration:run
```

`migration:run` builds first, so `dist/` is always current.

### To roll back

```bash
npm run migration:revert
```

This drops the 22 indexes and touches no data. `pg_trgm` is deliberately left
installed — dropping an extension would break anything else that came to depend
on it.

## ⚠️ Index/query coupling to keep in mind

`IDX_users_search_trgm` indexes a **concatenated expression**. Postgres only
uses an expression index when the query's expression matches the index's
exactly. That expression is generated by `buildUserSearchExpression()` in
`src/users/constants/user-search.constant.ts`.

**Editing either one without the other silently turns admin user search back
into a full sequential scan** — no error, just a slow query. If you change the
searchable columns, write a new migration that rebuilds the index to match.

## Folded into `ConsolidatedSchema`: `AffiliateProgram`

> No longer a separate file — collapsed into `1785500000000-ConsolidatedSchema`.
> The verification table and the `PARTNER_JWT_SECRET` requirement below still
> apply.

### What it does

Creates six new tables (`affiliate_settings`, `partners`, `referrals`,
`referral_clicks`, `partner_commissions`, `partner_payouts`), their enum types,
indexes and foreign keys, and seeds one settings row. **No existing table,
column or row is touched.**

### It ships switched off

`affiliate_settings.isEnabled` defaults to `false`. Until an admin turns the
programme on from **Admin → Affiliate → Programme**, nothing attributes,
accrues or pays out. Applying this migration is inert.

### ⚠️ `PARTNER_JWT_SECRET` is now required

Config validation rejects a missing value, and rejects one equal to
`JWT_SECRET`. Set a distinct secret in the deploy environment before deploying,
or the server will not boot.

## Applied: `1787500000000-ConsolidatedPipelineSchema`

### What it does

Collapses the ten migrations that sat between `UserTags` and today into one.
None of them had ever been committed, so they existed only in working trees —
replaying them one at a time would have recreated a history that never ran
anywhere real. Several were patches to each other: `Leads` created a `tld`
column that `DropLeadTld` removed four migrations later, `LeadTriage` appended
a value to an enum `Leads` had just defined, and `PipelineGatesInDb` added two
knobs to a table `LeadPipelineSettings` had created immediately before.

Collapsed: `OnboardingReminders`, `OneDebitPerMessage`, `Leads`,
`LeadIndiaSignals`, `BrowserEnrichment`, `LeadTriage`, `LeadLiveness`,
`DropLeadTld`, `LeadPipelineSettings`, `PipelineGatesInDb`.

Creates seven tables (`onboarding_reminders`, `leads`, `lead_ingest_runs`,
`lead_outreach_events`, `outreach_suppressions`, `lead_pipeline_settings`,
`wallet_transaction_duplicate_debits`), nine enum types, and the partial unique
index `UQ_wallet_tx_otp_usage_debit` that makes one-debit-per-message a database
invariant rather than an application convention.

### What changed in the fold, deliberately

- **`leads.tld` is never created**, so it is never dropped and `IDX_leads_tld`
  never exists. The classifier still resolves the effective TLD internally to
  decide keep/drop — it just stops being persisted.
- **`'parked'` is a value of `leads_enrichmentstatus_enum` from the start**
  rather than an `ALTER TYPE ADD VALUE`, which retires that migration's caveat
  about adding enum values inside a transaction. It is listed last so the enum
  sort order matches what the ten-step sequence produced.
- **`lead_pipeline_settings` is created with `ingestEnabled` and
  `livenessEnabled` already on it.**

The duplicate-debit handling from `OneDebitPerMessage` is preserved verbatim,
including the narrowed-predicate fallback and the refund worklist. Nothing is
deleted, rewritten or neutered in the ledger.

### It ships inert

The onboarding sweep still requires `ONBOARDING_REMINDERS_ENABLED`, and every
leads consumer — ingest scheduler, liveness prober, enrichment sweep, outreach
sender — is env-gated off by default. A deployment that sets none of the new
variables gains empty tables and nothing else. Every knob in
`lead_pipeline_settings` is NULLABLE and NULL means "use the env default", so
the seeded singleton row overrides nothing.

### Note for machines that already ran the ten

Nothing to do. The old rows stay in the `migrations` table naming files that no
longer exist, exactly as `PerformanceIndexes`, `AffiliateProgram` and
`AffiliateAccrualWatermark` still do after the previous consolidation. TypeORM
only cares that a name is present, so the extra rows are inert; the new
migration then applies as a no-op because every statement in it is
`IF NOT EXISTS` or catalogue-guarded.

## ⚠️ Do not use `migration:generate` on this schema

This project writes migrations by hand. Running `migration:generate` produces a
migration that **drops 21 of the performance indexes**, because they are
deliberately not declared on the entities:

- trigram GIN indexes (`IDX_users_search_trgm`, `IDX_messages_phoneNumber_trgm`)
  cannot be expressed with TypeORM decorators at all;
- several are partial indexes tuned for specific query shapes.

It will also propose renaming every explicitly-named foreign key to a hash.
Both are cosmetic churn at best and a serious performance regression at worst.
Write new migrations by hand, and use `migration:generate` only as a *read-only
diffing tool* when checking that entities and schema agree.

## Housekeeping note

Production contains a stray table, `v_user_id` (a single `uuid` column, one
row). It is not referenced by any entity or migration and looks like the
residue of an ad-hoc `CREATE TABLE … AS SELECT`. Nothing in this change touches
it; drop it separately once you have confirmed it is unused.
