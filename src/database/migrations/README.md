# Running migrations

## ⚠️ `migration:run` targets whatever `.env` points at

`src/database/data-source.ts` calls `dotenv.config()`, so `npm run migration:run`
reads `server/.env` — which is currently your **production RDS instance**.

`dotenv` does not override variables already present in the environment, so you
can safely aim a run somewhere else by exporting them inline:

```bash
DATABASE_HOST=localhost DATABASE_NAME=sm_verify \
DATABASE_USERNAME=postgres DATABASE_PASSWORD=… \
npm run migration:run
```

Always confirm the target before running:

```bash
npm run migration:show    # lists applied [X] and pending [ ] migrations
```

## Pending: `1785024000000-PerformanceIndexes`

### What it does

Creates the `pg_trgm` extension and 22 indexes. **Nothing else.** No table,
column, constraint, enum or row is created, altered or dropped, so no user data
can be lost by running or reverting it.

### Cost

- Adds roughly **24 MB** of index data at current volumes.
- Each `CREATE INDEX` briefly holds an ACCESS EXCLUSIVE lock on its table.
  At current sizes (largest table ~49k rows) every build is well under a
  second, so the total write pause is a few seconds at most.
- Every statement is `IF NOT EXISTS`, so re-running is a no-op.

### To run

```bash
cd server
npm run migration:show    # confirm PerformanceIndexes is pending
npm run migration:run
```

`migration:run` builds first, so `dist/` is always current.

### To roll back

```bash
npm run migration:revert
```

This drops the 22 indexes and touches no data. `pg_trgm` is deliberately left
installed — dropping an extension would break anything else that came to depend
on it.

### Zero-lock alternative

Only needed if you are applying this to a much larger dataset and cannot take
even a sub-second write pause. `CREATE INDEX CONCURRENTLY` cannot run inside a
transaction, and TypeORM wraps migrations in one, so it has to be applied by
hand:

```bash
psql "$DATABASE_URL" -f src/database/migrations/sql/1785024000000-performance-indexes.concurrent.sql

# then record it so TypeORM does not rebuild the same indexes
psql "$DATABASE_URL" -c "INSERT INTO migrations (timestamp, name)
  VALUES (1785024000000, 'PerformanceIndexes1785024000000');"
```

If a concurrent build is interrupted it leaves an INVALID index behind. Find and
retry it with:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
```

is selective.

## ⚠️ Index/query coupling to keep in mind

`IDX_users_search_trgm` indexes a **concatenated expression**. Postgres only
uses an expression index when the query's expression matches the index's
exactly. That expression is generated by `buildUserSearchExpression()` in
`src/users/constants/user-search.constant.ts`.

**Editing either one without the other silently turns admin user search back
into a full sequential scan** — no error, just a slow query. If you change the
searchable columns, write a new migration that rebuilds the index to match.
